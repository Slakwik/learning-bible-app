Обновлено: 15.09.2026. **Статус: запланировано, реализация отложена пользователем.**

План продолжает готовое нативное приложение, без переписывания архитектуры. Номера выпусков ниже — рабочие ориентиры, даты пока не назначены. Чекбоксы отмечать только после выполнения критериев и записи результатов проверки.

## Очерёдность и границы выпусков

**Уточнение после проверки синхронизации на сайте:** для пользователя основной сценарий — урок внутри класса. Текущий Android отправляет только личные ответы; их отсутствие в классе не является потерей при отправке. D1/D2 следует выполнять как ближайшую функциональную доработку после необходимых проверок хранения и синхронизации, раньше косметических улучшений C. Подробности и критерии: [совместимость с классами](android-class-integration.md).

| Этап | Результат | Зависимости | Условие перехода |
| --- | --- | --- | --- |
| A · следующий preview | Предсказуемая сборка, перенос данных и постоянная подпись | Доступ к ключу у владельца; тестовый телефон | Перенос debug → release и release → release проверен |
| B · кандидат для личного использования | Проверенная сохранность ответов и синхронизация | A, тестовая среда Firebase | Все критические сценарии данных проходят |
| C · чтение и материалы | Удобство чтения, обновление каталога | B; публикация feed в проекте сайта | Приёмка интерфейса и отказоустойчивости каталога |
| D · учебные группы | Классы, расписание, объявления, ответы класса | B; отдельная проверка модели прав | Изоляция классов и отзыв доступа подтверждены |

Приоритет P0 означает блокер безопасного распространения, P1 — следующий полезный этап, P2 — после стабилизации. Изменения сайта и Firebase выполнять отдельными задачами с учётом их среды и данных.

## A. Дистрибуция и перенос данных

### A1 · P0 · Воспроизводимая сборка

- [ ] Добавить Gradle Wrapper для используемой версии 8.10.2 и SHA-256 дистрибутива.
- [ ] Перевести CI на Wrapper; сохранить Java 17 и SDK 35 до отдельной проверки обновлений зависимостей.
- [ ] Сохранять отчёты тестов/Lint при неуспехе и APK только после успешных проверок.
- [ ] Разобрать 12 предупреждений: для каждого записать исправление или причину отсрочки; ошибки Lint не подавлять общей настройкой.

**Файлы:** `android/gradle*`, `android/app/build.gradle`, `.github/workflows/android.yml`.

**Приёмка:** чистый checkout собирается через Wrapper; 7 + 22 существующих теста проходят; артефакты связаны с конкретным коммитом.

### A2 · P0 · Безопасный импорт экспортированных ответов

Зависит от анализа текущего формата `AnswerStore.export`. Не считать существующий экспорт готовым решением переноса, пока обратная загрузка не проверена.

- [ ] Описать версионированный формат экспорта, владельца, ответы и обе версии конфликтов; определить совместимость с уже выпущенным JSON.
- [ ] Добавить выбор JSON через системный диалог, ограничения размера, проверку структуры и предварительный просмотр количества уроков/конфликтов.
- [ ] Обработать неизвестные уроки и поля без молчаливого удаления: показать отчёт и сохранить исходный файл.
- [ ] Требовать явный выбор назначения гостевых/старых черновиков; не присваивать данные автоматически другому аккаунту.
- [ ] Сливать импорт с локальными данными транзакционно; при разногласии сохранять обе версии; отмена и ошибка не меняют базу.
- [ ] Сделать повторный импорт предсказуемым, без дублей и автоматической отправки гостевых данных.

**Файлы:** `AnswerStore.kt`, `SettingsActivity.kt`, JVM-тесты формата и хранения; имена новых компонентов выбрать при реализации.

**Приёмка:** экспорт → чистая установка → импорт сохраняет тексты, пустые ответы и конфликтные версии; проверены повреждённый файл, другой UID, отмена и повторный импорт.

### A3 · P0 · Постоянная подпись и переход с debug

Зависит от A2 для переноса несинхронизированных данных.

- [ ] Создать/подключить постоянный release-ключ и резервную копию у владельца; ключи и пароли не помещать в Git.
- [ ] Настроить предусмотренные workflow GitHub Secrets и проверку подписи готового APK.
- [ ] Зафиксировать applicationId, правила увеличения versionCode и порядок выпуска тегов.
- [ ] Проверить переход с текущего debug APK; при несовпадении сертификатов документировать экспорт, проверку файла, переустановку и импорт.
- [ ] Проверить две сборки с постоянным ключом: обновление поверх установленной версии сохраняет ответы, закладки и настройки.
- [ ] Публиковать APK, SHA-256, версию, ссылку на CI и известные ограничения; не называть debug сборку стабильной.

**Приёмка:** проверены оба пути перехода на тестовых данных; владелец располагает резервной копией ключа; инструкция не требует удалять единственную копию черновиков.

## B. Ответы и синхронизация

### B1 · P0 · Проверка Android/Firebase-конфигурации

- [ ] Сверить package name, Android-регистрацию, публичную конфигурацию, ограничения ключа и режим App Check.
- [ ] Подготовить тестовое подключение к Auth/Firestore Emulator без обращения к рабочим данным.
- [ ] Проверить вход, неверный пароль, отсутствие сети, истёкшую сессию, выход и повторный вход.
- [ ] Реальный вход проверить отдельно на выделенном тестовом аккаунте; зафиксировать результат без паролей и токенов.

**Файлы:** `App.kt`, `LoginActivity.kt`, настройки тестового окружения.

**Приёмка:** пользователь получает понятную ошибку; неуспешный вход не меняет владельца локальных данных; тестовые запуски не пишут в production.

### B2 · P0 · Матрица сохранности ответов

- [ ] Добавить интеграционные сценарии из таблицы ниже, сохранив существующие модульные тесты.
- [ ] Проверить последовательную запись при быстром вводе, уходе из урока и завершении процесса.
- [ ] Проверить переключение аккаунта при чтении/отправке и запоздалые ответы сети.
- [ ] Проверить сетевые ограничения ручной синхронизации и WorkManager, включая режим энергосбережения Samsung.
- [ ] Для каждого исправленного сбоя добавить регрессионную проверку поведения.

**Файлы:** `AnswerStore.kt`, `Sync.kt`, `SyncPolicy.kt`, `LessonActivity.kt`, тесты.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Гость → A → B → гость | Ответы и закладки принадлежат исходному владельцу |
| Ввод офлайн → завершение процесса → открытие | Последний подтверждённый локально текст сохранён |
| Сбой/таймаут отправки → повтор | Изменения остаются ожидающими отправки, дублей нет |
| Изменение разных вопросов на двух клиентах | Оба изменения сохраняются |
| Разные тексты одного вопроса | Две версии доступны для явного выбора |
| Удаление текста последнего ответа | Пустое значение сохраняется и синхронизируется |
| Ввод во время отправки старой версии | Более новый ввод остаётся локально и не теряется |
| Выход во время сетевого запроса | Поздний результат не применяется к другому аккаунту |
| Разрешение конфликта → повторный запуск | Выбор сохранён, конфликт не исчезает без решения |

**Приёмка:** матрица проходит на тестовом окружении; отчёты приложены к выпуску; ошибки сети не помечают данные синхронизированными.

- [ ] Проверить два веб-клиента и Android, включая запоздалую запись старой вкладки.
- [ ] Подготовить порядок публикации и отката, сохраняющий совместимость клиентов.

**Приёмка:** конкурентная запись сайта больше не теряет изменения телефона; до выполнения задача остаётся явным ограничением релиза.

## Как продолжить позднее

1. Прочитать этот план, `AGENTS.md` и `android/README.md`; проверить `main`, последний релиз и незакоммиченные изменения.
2. Начать с A1: это не требует изменения production Firebase или сайта.
3. Затем выполнить A2 и подготовить A3; перед переходом с debug подтвердить возможность восстановления экспорта.
4. Получить доступ к тестовому телефону и тестовой Firebase-среде для B1/B2; независимые автоматические проверки выполнять до ручной приёмки.
5. В каждой задаче сохранять кратко: что изменено, как проверено, ссылки на CI/коммит, оставшиеся ограничения. Критерии без проверки не отмечать выполненными.
6. Перед выпуском проверить diff, тесты, подпись, обновление и заметки релиза. Дату и окончательный состав выпуска определить по результатам приёмки.

### Решения, которые понадобятся при реализации

- Где владелец хранит постоянный ключ и резервную копию.
- Какие устройства доступны для ручной проверки и кто выполняет её.
- Какие тестовые аккаунты/окружение использовать для настоящего входа.
- Когда отдельно дорабатывать и публиковать веб-редактор и feed.
- Какой минимальный объём функций классов включить в первый групповой выпуск.

Эти вопросы не блокируют сохранение плана. Автоматический запуск работ и напоминания не назначены; продолжение — по следующему запросу пользователя.
